⏺ How large is it?

  I measured the current llama.cpp release (b12651, published today). The
  upstream archives come with ~20 tools. llama-server only needs its executable,
  libllama-server-impl, libllama, libllama-common, libmtmd, and the ggml
  libraries.

  - Expect about 12–33 MB more per installer. Vulkan adds ~45 MB on its own
    (ggml-vulkan.so/.dll), so it roughly doubles the Linux and Windows cost.
  - Linux and Windows x64 can be trimmed. They ship 15 CPU-variant libraries
    (~20 MB) for different processor generations. Keeping about 5 of them saves
    ~12 MB.
  - The model is the real size. A usable GGUF model is 1–5 GB, so it should be
    downloaded at runtime, not bundled.

  Plan

  1. Fetch script (scripts/fetch-llama-server.js)
  - Pin the version in package.json (e.g. "llamaCppTag": "b12651") and keep
    SHA-256 checksums in a committed file.
  - Download the asset for each platform and arch, verify it, and extract only
    the server set into vendor/llama-server/<platform>-<arch>/. Include
    llama.cpp's MIT LICENSE.
  - For macOS universal, combine each arm64/x64 binary pair with lipo so both
    slices get identical files. @electron/universal merges identical files
    without complaint.
  - Add vendor/ to .gitignore. It is already in the packager ignore list in
    gulpfile.js, which is fine because the files go in through --extra-resource.

  2. Packaging
  - Right now electronite-build-* packages several archs in one call
    (--arch=x64,arm64), and --extra-resource can't change per arch. Split these
    into one packager call per arch, each with
    --extra-resource=vendor/llama-server/<plat>-<arch>. The files then land in
    resources/llama-server/ (Contents/Resources/ on Mac), outside the app code.
  - Check that the gulp release-* tasks (dmg, deb, Windows installer) still find
    the dist/ folders under the same names, and that the deb keeps the
    executable bit.

  3. Main process (electronite/llamaServerManager.js)
  - Find the binary: process.resourcesPath/llama-server in packaged builds,
    vendor/... in dev.
  - Start it with --host 127.0.0.1 --port <free port> and either -m <model> or a
    models directory. Wait for /health to respond. Kill it on before-quit, when
    the window closes, and if it crashes.
  - Add IPC handlers next to exposeAiApiQueryToMainWindow(), such as
    ai-apis:local-start, local-stop and local-status, limited to the main window
    like the existing ones. The current OpenAI-compatible client then just
    points at http://127.0.0.1:<port>, and prompt-prefix caching already works
    with llama-server.

  4. Model management (separate piece of work)
  - Download a GGUF model into the user data folder, with progress and resume.
    The existing download manager in electronite/index.js might be reusable.

  5. CI (.github/workflows/main.yml)
  - Add a step before npm run build-* in each of the three build jobs to run the
    fetch script, cached with actions/cache keyed on the pinned version.

  6. Platform risks
  - Windows ia32: no upstream build. Building it from source for x86 isn't
    officially supported. I recommend turning the local server off on ia32.
  - Linux: the upstream builds are made on a recent Ubuntu, so they may need a
    newer glibc than older distros have. Test on the oldest distro you support,
    or build from source in the existing photonomad/github_build Docker image.
  - macOS: CI doesn't sign builds now, so the nested binaries are unsigned too.
    Signing or notarizing later would need these binaries signed with
    hardened-runtime entitlements.
  - Windows: Defender or SmartScreen may flag a new .exe that opens a port.
    Binding to localhost only helps.

  Decisions for you

  1. CPU-only or Vulkan on Windows/Linux x64? CPU-only costs ~18 MB; Vulkan
     costs ~33 MB but gives GPU speed. Another option is CPU-only in the
     installer, with Vulkan downloaded on demand.
  2. Windows ia32: turn the feature off there (my recommendation), or try
     building it from source?
  3. Trim the CPU variants on x64 to save ~12 MB?

  Once you've decided, I can start with the fetch script and the per-arch
  packaging split.

  GPU only?  and is there a savings with GPU only support?                      

  Ran 1 shell command (ctrl+o to expand)

⏺ No, GPU-only doesn't save anything. It costs more than CPU-only.

  Why:
  - The Vulkan build can't drop the CPU backend. llama.cpp won't load a model
    without one. Even with every layer on the GPU, the CPU still handles
    tokenizing, sampling and some operations. So the Vulkan build is the CPU
    build plus ~45 MB for ggml-vulkan.
  - What you can drop is most of the 15 CPU-variant libraries. If the GPU does
    the heavy work, the CPU part barely matters. Keeping just the baseline x64
    variant plus haswell is enough.

  ┌─────────────────────────┬───────────┬─────────────────────────┐
  │       x64 option        │ Installed │ Compressed in installer │
  ├─────────────────────────┼───────────┼─────────────────────────┤
  │ CPU-only (all variants) │ 46–49 MB  │ ~18–19 MB               │
  ├─────────────────────────┼───────────┼─────────────────────────┤
  │ Vulkan (all variants)   │ 90–94 MB  │ ~32–33 MB               │
  ├─────────────────────────┼───────────┼─────────────────────────┤
  │ Vulkan, 2 CPU variants  │ 72–75 MB  │ ~25–26 MB               │
  └─────────────────────────┴───────────┴─────────────────────────┘

  The trimmed Vulkan build costs about 7 MB more per installer than CPU-only and
  about 7 MB less than the full Vulkan build. The ranges cover Linux and
  Windows.

  Things to know about Intel integrated GPUs:
  - Vulkan support varies by age. Intel GPUs from Skylake (2015) onward support
    it reasonably well. Older ones are spotty or buggy.
  - They're often not faster than the CPU. These GPUs share system memory, so
    generation speed is limited by memory bandwidth either way. The big gains
    come from dedicated NVIDIA/AMD cards and the newer Intel Arc/Xe GPUs.
  - It still works without a usable GPU. If no Vulkan device is found,
    llama-server runs on the CPU. Since GPU-only isn't possible anyway, the
    Vulkan build covers both cases.
  - On Linux it needs the system's Vulkan library (libvulkan.so.1). The deb
    should depend on libvulkan1 and mesa-vulkan-drivers. On Windows the GPU
    drivers already include it.
  - macOS doesn't change. Its builds already use Metal for the GPU and are the
    smallest.

  My recommendation: ship the Vulkan build trimmed to 2 CPU variants on Linux
  x64, Linux arm64 and Windows x64. It's ~26 MB per installer, one build per
  platform, and GPU speed for users who have a capable card.

⏺ No. llama.cpp doesn't publish a universal macOS llama-server. It ships
  separate macos-arm64 and macos-x64 builds. The xcframework asset is a library
  for embedding llama.cpp in Swift/Xcode apps and doesn't include llama-server.

  You can make one yourself, though. I tried it with lipo on the b12651
  downloads and it combined cleanly:

  - Size: 58 MB installed, about 24 MB compressed. That matches the plan's
    estimate.
  - Result: llama-server and all the shared libraries contain both x86_64 and
    arm64.
  - One wrinkle: the Intel build doesn't use Metal, so libggml-metal exists only
    in the arm64 build. That's fine: the Intel half of llama-server never loads
    it, so it can stay arm64-only.
  - Not tested: the auto-mode safety check blocked running the downloaded
    binaries, so I haven't confirmed that either half starts. If you want to
    check, run ! .../universal/llama-server --version yourself, and again with
    arch -x86_64 in front. You'll need to add the .dylib symlinks first.

  Two options for the build:
  1. Combine the upstream builds with lipo in the fetch script (recommended). It
     takes a few seconds, needs no compiler, and uses the same pinned version
     as the other platforms.
  2. Build from source in the macOS CI job with
     CMAKE_OSX_ARCHITECTURES="arm64;x86_64". It adds roughly 5–10 minutes per
     build. It only makes sense if you need custom build options.

  Packaging details for option 1:
  - Put the same combined set in both halves of the app. @electron/universal
    errors out if a file exists in only one half. If both halves get identical
    files, it copies them as they are.
  - Keep the .dylib symlinks (e.g. libllama.1.dylib → libllama.1.0.0.dylib) when
    copying.
  - Re-sign afterwards with codesign --force -s - on each file. Apple Silicon
    won't run unsigned code, and an unsigned app can't sign its contents
    properly. This would change to a real signing identity if you add signing
    later.
  - The x64-only DMG can just use the upstream x64 build as it is, which is
    about 12 MB compressed.

  decision from before?

⏺ I wrote the fetch script, scripts/fetch-llama-server.js, and ran it for all
  five targets. Each one extracted cleanly, and every library the kept files
  need is present. A second run correctly skipped all of them as already up to
  date. I haven't started any of the binaries; that's the smoke test planned for
  step 2.

  How to run it:
  - npm run fetch-llama-server fetches the targets the current OS builds: both
    Mac versions on macOS, both Linux versions on Linux, win32-x64 on Windows.
  - Add -- --all for every target, -- --targets=linux-x64,win32-x64 for specific
    ones, or -- --force to extract again.
  - After bumping llamaCppTag in package.json, run -- --update-checksums to
    refresh the checksums file.

  What it does:
  - Version and checksums: the release is pinned by a new "llamaCppTag": 
    "b12651" in package.json. Downloads are checked against
    scripts/llama-server-checksums.json, which comes from the sha256 checksums
    GitHub publishes for each release file.
  - Download: archives are cached in vendor/llama-server/.cache/. A failed
    download never leaves a partial file behind.
  - Files kept: chosen by pattern rather than a fixed list, so new libraries in
    future releases are picked up automatically. It keeps llama-server, the
    license files, and the shared libraries, and drops the other tools'
    libraries and the unused CPU variants. Linux arm64 keeps only the armv8.0_1
    variant, per your answer.
  - Symlinks and the executable bit are kept for the Mac and Linux targets.
  - Up-to-date check: each target folder gets a .llama-server.json file
    recording the version and file list, which is how it knows to skip.

  What the script does:
  - Finds each packaged app in dist/ and copies the matching files from
    vendor/llama-server/<target>/:
    - The Mac apps get them in <app>.app/Contents/Resources/llama-server/; the
      universal app gets both versions.
    - Linux and Windows get them in resources/llama-server/<target>/.
    - win32-ia32 is skipped with a message.
  - Copies the files as they are, keeping symlinks and the executable bit.
  - Checks each copy:
    - llama-server is present and executable.
    - No symlinks are broken.
    - The executable is built for the expected processor. It reads the file
      header for this, so it doesn't need the file tool.
  - Smoke test: runs llama-server --version once per version this machine can
    run. That's darwin-arm64 (plus darwin-x64 under Rosetta) on Mac, linux-x64
    on the Linux job, and win32-x64 on Windows. The arm64 Linux build only gets
    the header check, because the x64 Linux machine can't run it.
  - Fails the build if a vendor folder is missing (it prints the fetch command
    to run), if a packaged folder doesn't match any known target, or if a check
    or the smoke test fails.
  - Options: --dist=<dir>, and --no-smoke-test (or
    LLAMA_SERVER_SKIP_SMOKE_TEST=1) to skip the smoke test.

  Other changes:
  - package.json: build-macos, build-linux and build-win now run the fetch
    before packaging and the copy after it. The fetch skips anything already up
    to date. So the GitHub workflow needs no changes; caching downloads there is
    optional.
  - scripts/deb/DEBIAN/control: added Recommends: libvulkan1, 
    mesa-vulkan-drivers and raised Installed-Size to 557000. That size is a
    rough figure for the larger x64 build, because one control file serves both
    Linux architectures.

  one llama.cpp builds against, the linux-x64 smoke test will fail. That's the

  electronite/llamaServerManager.js:
  - Picking the build: it looks in process.resourcesPath/llama-server when
    packaged, or vendor/llama-server in development. Apple Silicon Macs get the
    arm64 build, even when the user forces the app to run under Rosetta, and it
    falls back to darwin-x64 if that's the only one there. Windows ia32 reports
    the server as unavailable.
  - start({ model, alias?, contextSize?, gpuLayers?, cpuOnly?, extraArgs?, 
    startTimeoutMs? }):
    - It requires an existing .gguf file.
    - It picks a free port on 127.0.0.1, starts llama-server with --no-ui and
      --alias <model name>, and resolves once /health returns 200. The wait is
      up to 5 minutes, since loading a large model can be slow.
    - Calling it again with the same options returns the running server;
      different options restart it.
    - cpuOnly passes --n-gpu-layers 0, the escape hatch for bad GPU drivers.
  - Security:
    - The server only accepts connections from this machine.
    - Each start creates a random API key and hands it to llama-server through
      the LLAMA_API_KEY environment variable, so it doesn't appear in process
      lists.
    - Other programs and web pages on the machine can't use the server without
      that key.
  - getStatus() returns available, state, baseUrl, apiToken, model, alias, pid,
    version (the bundled llama.cpp version), lastError and the last 50 log
    lines.
  - Failures:
    - If llama-server exits while starting, the error includes the tail of its
      log.
    - A crash after it started is recorded in lastError.
    - stop() asks the process to exit and force-kills it after 5 seconds.

  Wiring:
  - electronite/index.js: adds the IPC handlers ai-apis:local-server-start,
    -stop and -status, limited to the main window like the existing ones. It

  - electronite/preloadAiApi.js: adds window.AiAPIs.localServer.{start, stop,

❯ do llama server queries run over a port, or is it a direct application call?  

⏺ It runs over a port. Nothing calls llama-server directly; every query is an
  HTTP request over the machine's local network interface (127.0.0.1):

  1. Checking tool to main process: the checking tool calls
     window.AiAPIs.query(...) in the renderer, which goes to the main process
     over Electron IPC (ai-apis:query).
  2. Main process to llama-server: queryAiApiFromMainProcess sends an HTTP POST
     to http://127.0.0.1:<port>/v1/chat/completions, with the reply streamed
     back. This is the same client code used for LM Studio. The port is chosen
     at random each time the server starts.
  3. Router to model process: in router mode, llama-server is a separate process
     that sends the request on to the process for the loaded model, again over
     a local port.

  Why that's fine:
  - Speed: a local HTTP round trip costs well under a millisecond. Generating a
    reply takes seconds, so the hop doesn't matter.
  - Crash isolation: llama-server is a separate process, so a crash in it or in
    a GPU driver can't take down tC. The manager just records the error.
  - No extra code: the same OpenAI-style API client works for LM Studio, the
    bundled server, or a remote one.

  The cost is that it's a network port, though only reachable from this machine:
  - Other machines can't connect, because it listens on 127.0.0.1 only.
  - Other programs and web pages on the same machine can reach the port but get
    401 without the random per-start API key. The key goes to llama-server
    through an environment variable, so it isn't visible in the process list.
  - The per-model processes in router mode also listen on local ports. The open
    question from before applies here: whether they enforce the API key too.
  - Firewalls: some desktop firewalls or security tools may prompt when a new
    program opens a port, even a local-only one.

  If you want to avoid a TCP port:
  - Unix socket or Windows named pipe: I believe recent llama-server builds can
    listen on a socket file instead of a port, but I haven't checked that this
    version supports it. It would also need a small change to the HTTP client,
    and the router's own processes might still use ports.
  - Calling llama.cpp directly inside tC: this would mean a native Node module
    such as node-llama-cpp. It removes the port, but you'd have to rebuild the
    native module for each Electron version and architecture. It would also lose
    the crash isolation and router mode, and it would replace the prebuilt
    llama.cpp releases this plan relies on.

  I'd stay with HTTP on 127.0.0.1 plus the API key. If you want, I can check
  whether the bundled version supports socket files.

❯ should we pick a unique port number for it?  should we make it dynamic to     
  pick an unused port?                                                          

⏺ It already picks an unused port each time it starts, and I'd keep it that way.
  The manager asks the operating system for a free port on 127.0.0.1 and starts
  llama-server on it (getFreePort() in llamaServerManager.js). Callers never
  need the number: they pass localServer: true, or read baseUrl from
  getStatus().

  Why not a fixed port:
  - Collisions: other tools use well-known ports, such as LM Studio on 1234,
    Ollama on 11434 and llama-server's own default of 8080. A fixed port could
    collide with these or with any other app. Picking a less common number only
    makes a collision less likely, not impossible.
  - Multiple users on one machine: two people running tC at the same time would
    fight over a fixed port.
  - Leftover processes: if tC crashed and left an old llama-server running, a
    fixed port would stay taken until someone killed it by hand. A new free port
    just works.
  - No benefit for outside tools: connecting another app to the server would
    also need the API key, which changes on every start. So a fixed port doesn't
    make that possible either.

  One gap worth fixing: there's a split second between finding the free port and
  llama-server claiming it, and another program could grab it in between. It's
  very unlikely, but when it happens llama-server exits and start() fails with a
  "couldn't bind" error. The fix is small: if startup fails because the port
  was taken, pick a new port and retry, say up to 3 times.

  If you later want a fixed port (for example, so users can point other tools at
  the server), I'd add it as an optional preferred-port setting that falls back
  to a free port when taken. That only makes sense if the API key could also be
  fixed or shown to the user.

⏺ I added the port retry and made sure llama-server stops with tC, including
  when tC crashes. All 20 manager tests pass, along with the licenses test, and
  lint is clean. It still hasn't run against a real llama-server.

  Port retry:
  - When it retries: if llama-server exits during startup and the port is now
    held by another program, start() picks a new free port and tries again, up
    to 3 attempts. It also retries if the log says the port couldn't be bound.
    It checks whether the port is taken rather than relying only on the log,
    because I couldn't find llama-server's exact bind-error message in the
    binary.
  - Other failures don't retry: a bad models folder, a crash, or a missing
    binary fail straight away, with the log tail.
  - Readiness check: "ready" now needs both /health and a /v1/models request
    using our API key to succeed. Another program that happened to grab the port
    and answers /health isn't mistaken for our server.

  Stopping when tC stops:
  - Normal quit: the server and the per-model processes it started are killed on
    will-quit, as before. They're now also killed on process.on('exit'), which
    covers app.exit() and other exits that skip will-quit.
  - Windows: stopping now ends the whole process tree with taskkill /t /f.
    Previously only the server itself was killed, which would have left the
    per-model processes running. Mac and Linux kill the process group.
  - tC crashes or is force-killed: no quit code runs in that case, so a PID file
    at <userData>/llama-server.pid records the running server. On the next
    launch, cleanupOrphan() kills the leftover server. Because process IDs get
    reused, it first checks that the recorded process is still a llama-server,
    using ps or tasklist. The file is removed when the server stops normally.

  Tests added:
  - Retrying after the port is taken twice.
  - Giving up after 3 attempts.
  - No retry for other failures.
  - Writing and removing the PID file, including on the quit path.
  - Leaving an unrelated process with a reused PID alone.
  - Killing a real leftover process named llama-server: a symlink to node, so no
    downloaded binary runs. This test is skipped on Windows.

  One gap remains: if tC is force-killed, the server keeps running until tC is
  opened again. I don't know of a reliable way in Node to make the child process
